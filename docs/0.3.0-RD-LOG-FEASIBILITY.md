# HelioTerm 0.3.0 R&D: log-driven feasibility

Date: 2026-08-10

## Scope

This study changed only the `D:\code\HelioTerm` source branch. It did not install a plugin, change Codex Desktop configuration, refresh tool projection, change a model, or stop an existing task. The two rollout files were read in place and only aggregate counters were retained.

## What the logs show

The deterministic `rollout-metrics.mjs` parser replayed two active Desktop rollouts from the current rate-limit window.

| Metric | Heliolune task | Other active engineering task |
|---|---:|---:|
| Recorded total tokens | 114,765,535 | 43,357,458 |
| Cached input ratio | 97.773% | 97.372% |
| Sampling events | 872 | 360 |
| User messages | 10 | 5 |
| Samples per user message | 87.2 | 72.0 |
| `functions.exec` wrappers | 831 | 335 |
| Wrappers with exactly one nested tool | 90.73% | 98.51% |
| HT MCP or short-CLI wrappers | 173 | 196 |
| Model-visible tool-output bytes | 2,166,699 | 1,387,722 |

The dominant cost is repeated owner-model sampling over a large cached context, not the remaining compact output. Across both traces, 1,084 of 1,166 wrappers contained exactly one nested tool. HT reduced terminal evidence size, but a one-command-per-wrapper usage pattern still forced another Sol sampling request after nearly every command.

## Prototype A: read-only MCP batch

The existing direct runner already validates up to four operations and runs adjacent read-only observations concurrently. Version 0.2 did not expose that capability as one MCP tool. The 0.3 prototype adds a read-only `batch` tool with a shared working directory and two to four `{operation, argument}` entries.

A 25-round matched benchmark used Git status, recursive test discovery, package JSON inspection, and two-file counting:

| Measurement | Four individual observations | One batch | Change |
|---|---:|---:|---:|
| Owner/model tool round trips | 4 | 1 | -75.00% |
| Median local execution | 62.738 ms | 36.719 ms | -41.47% |
| MCP request payload | 744 bytes | 364 bytes | -51.08% |
| Compact response | 589 bytes | 251 bytes | -57.39% |

At the logged average input sizes, replacing four known observations with one call removes three sampling requests: about 394,668 raw context tokens in the Heliolune trace or 364,911 in the other trace. Most of those tokens were cached, so these are raw-context reductions, not provider billing claims.

Adoption is the limiting factor. The parser found 361 HT-related wrappers that contained exactly one nested tool. If 25% can safely be arranged into complete four-operation groups, the scenario removes 66 sampling requests, roughly 8.4 million raw context tokens at the combined observed average. A 50% grouping scenario removes 135 requests, roughly 17.3 million raw context tokens. Dependency-driven commands cannot be combined without changing owner intelligence and are excluded from the safe design.

The tool-list schema grows from 9,815 to 10,755 UTF-8 bytes: +940 bytes, or about 235 content tokens with the repository's labelled bytes/4 estimator. This is a one-tool deferred-projection overhead and is far smaller than one eliminated logged sampling request, although the exact Codex quota weighting remains unavailable.

## Prototype B: deterministic rollout metrics

`rollout-metrics.mjs` reads token-count and tool-envelope metadata without retaining prompts, command strings, or outputs. It reports cache ratio, token deltas, samples per user message, wrapper fan-out, HT routing counts, output bytes, and rate-limit percentage changes. This corrects the 0.2 meter's blind spot: bytes/4 remains useful for terminal content, but it cannot reveal the much larger cost of repeated cached-context sampling.

The parser is suitable as an offline benchmark and diagnostics command. It should not run automatically on every terminal call: scanning a growing rollout would add I/O, create a privacy boundary, and not reduce model usage.

## Feasibility decisions

| Candidate | Feasibility | Expected value | Decision |
|---|---|---|---|
| Read-only MCP `batch` | High | High for repo intake, parallel checks, and final verification | Keep in 0.3 prototype |
| Privacy-preserving rollout metrics | High | High for truthful optimization and regression detection | Keep as offline diagnostics |
| Arbitrary `terminal_batch` | Medium | Potentially covers stale-session short-CLI calls | Defer until ordered failure, mutation, and approval semantics are specified |
| Automatic intelligent command chaining | Low/medium | Could remove dependent round trips | Reject for now; it would move planning into HT and risk lowering owner intelligence |
| More Luna compression | High technically | Low current value; Luna was a small share of observed raw use | Do not prioritize |
| Automatic rollout scanning on every call | High technically | Low and privacy-sensitive | Reject |

## Release gate still missing

The source prototype can prove local transport savings, schema safety, and deterministic log metrics without changing Codex. It cannot yet prove that Sol consistently selects `batch`, because a new MCP tool is visible only after installing the plugin and restarting Desktop. A later opt-in acceptance must compare matched fresh tasks and verify selection rate, task quality, latency, raw context tokens, cache ratio, and rate-limit movement before 0.3.0 is released.
