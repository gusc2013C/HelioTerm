# HelioTerm 0.3.0 R&D: log-driven feasibility

Date: 2026-08-10

## Scope

This study changed only the isolated `D:\code\HelioTerm-0.3-rd` worktree. The globally linked `D:\code\HelioTerm` checkout remains on stable 0.2. It did not install a plugin, change Codex Desktop configuration, refresh tool projection, change a model, or stop an existing task. The two rollout files were read in place and only aggregate counters were retained.

## What the logs show

The deterministic `rollout-metrics.mjs` parser replayed two active Desktop rollouts from the current rate-limit window.

| Metric | Aggregate |
|---|---:|
| Recorded total tokens | 180,090,382 |
| Cached input ratio | 97.830% |
| Sampling events | 1,374 |
| User messages | 16 |
| `functions.exec` wrappers | 1,285 |
| Wrappers with exactly one nested tool | 1,185 |
| HT single-tool wrappers | 374 |
| Read-only batch-eligible wrappers | 86 |
| Model-visible tool-output bytes | 3,824,541 |

The dominant cost is repeated owner-model sampling over a large cached context, not the remaining compact output. Across both traces, 1,185 of 1,285 wrappers contained exactly one nested tool. HT reduced terminal evidence size, but a one-command-per-wrapper usage pattern still forced another Sol sampling request after nearly every command. Only 86 wrappers are conservatively eligible for the read-only batch; arbitrary commands and dependent work are tracked separately.

## Prototype A: read-only MCP batch

The existing direct runner already validates up to four operations and runs adjacent read-only observations concurrently. Version 0.2 did not expose that capability as one MCP tool. The 0.3 prototype adds a read-only `batch` tool with a shared working directory and two to four `{operation, argument}` entries.

A 25-round real MCP client/server benchmark used Git status, recursive test discovery, metadata inspection, and file counting in three repositories:

| Measurement | Four individual observations | One batch | Change |
|---|---:|---:|---:|
| Owner/model tool round trips | 4 | 1 | -75.00% |
| HelioTerm MCP round trip | 67.054 ms | 38.013 ms | -43.31% |
| TactileGear MCP round trip | 64.841 ms | 37.033 ms | -42.89% |
| Heliolune MCP round trip | 68.546 ms | 39.157 ms | -42.88% |
| MCP request payload | 721–780 bytes | 335–373 bytes | -52.18% to -53.54% |
| Compact response | 499–591 bytes | 250–251 bytes | -49.90% to -57.53% |

At the logged combined average of 131,531 input tokens per sampling request, replacing four known observations with one call removes about 394,593 raw context tokens. Most were cached, so this is a raw-context reduction, not a provider billing claim.

Adoption is the limiting factor. The parser found 86 read-only batch-eligible single wrappers. At 25% adoption, complete four-operation groups remove 15 sampling requests, roughly 2.0 million raw context tokens. At 50%, they remove 30 requests and roughly 3.9 million tokens; the strict 100% upper bound is 63 requests and about 8.3 million tokens. Dependency-driven commands are excluded.

With both batch prototypes, the tool-list schema grows from 9,815 to 12,022 UTF-8 bytes: +2,207 bytes, or about 552 content tokens with the repository's labelled bytes/4 estimator. This deferred-projection overhead is far smaller than one eliminated logged sampling request, although the exact Codex quota weighting remains unavailable.

## Prototype B: sequential terminal batch

The logs contain 374 HT single-tool wrappers, but only 86 are read-only batch candidates. `terminal_batch` targets commands that Sol can already specify before seeing any intermediate output. It validates the whole list before starting, executes sequentially, stops on first failure, never parallelizes mutations, and exposes truthful destructive/open-world metadata.

A 15-round real MCP benchmark ran four separate Node programs in each repository. Four individual calls and one `terminal_batch` had effectively identical local work time: batch latency was 0.22% to 1.52% lower, as expected because execution remains sequential. The batch reduced owner/model round trips by 75%, request bytes by 42.00% to 43.00%, and compact response bytes by 65.52%. No speed claim is made for the child commands themselves; the benefit is removing owner resampling and transport envelopes.

The candidate passed 133 HelioTerm tests, including atomic validation, stop-on-failure, and a one-second whole-batch timeout that returned exit 124 without running the next command. Existing project suites also passed (Heliolune 188/188 and TactileGear 34/34) without test-created working-tree changes. The machine-readable snapshot is `benchmarks/results/0.3.0-rd-batching-2026-08-10.json`.

## Prototype C: deterministic rollout metrics

`rollout-metrics.mjs` reads token-count and tool-envelope metadata without retaining prompts, command strings, or outputs. It reports cache ratio, token deltas, samples per user message, wrapper fan-out, HT routing counts, output bytes, and rate-limit percentage changes. This corrects the 0.2 meter's blind spot: bytes/4 remains useful for terminal content, but it cannot reveal the much larger cost of repeated cached-context sampling.

The parser is suitable as an offline benchmark and diagnostics command. It should not run automatically on every terminal call: scanning a growing rollout would add I/O, create a privacy boundary, and not reduce model usage.

## Feasibility decisions

| Candidate | Feasibility | Expected value | Decision |
|---|---|---|---|
| Read-only MCP `batch` | High | High for repo intake, parallel checks, and final verification | Keep in 0.3 prototype |
| Privacy-preserving rollout metrics | High | High for truthful optimization and regression detection | Keep as offline diagnostics |
| Sequential `terminal_batch` | Medium/high | Covers preplanned arbitrary commands without parallel mutation | Keep in R&D; require multi-project and failure-path acceptance |
| Automatic intelligent command chaining | Low/medium | Could remove dependent round trips | Reject for now; it would move planning into HT and risk lowering owner intelligence |
| More Luna compression | High technically | Low current value; Luna was a small share of observed raw use | Do not prioritize |
| Automatic rollout scanning on every call | High technically | Low and privacy-sensitive | Reject |

## Release gate still missing

The source prototype can prove local transport savings, schema safety, and deterministic log metrics without changing Codex. It cannot yet prove that Sol consistently selects `batch`, because a new MCP tool is visible only after installing the plugin and restarting Desktop. A later opt-in acceptance must compare matched fresh tasks and verify selection rate, task quality, latency, raw context tokens, cache ratio, and rate-limit movement before 0.3.0 is released.
